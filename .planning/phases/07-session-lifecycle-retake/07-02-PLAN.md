<objective>
Give the operator a runtime knob for the log level, so the Agent event stream can
be observed at the level an event actually runs at without a redeploy.

Purpose: ROADMAP success criterion 5 has two halves and they are not the same
change. D-12 raises the AGT-04 event lines from `debug` to `info` (plan 07-05);
this plan supplies the "without a redeploy" half — a mechanism that changes the
process's level in place. Neither task in this phase may claim to satisfy both.

Output: `setLogLevel()` on the winston logger, a `SIGHUP`-driven reload of the
existing `LOG_LEVEL` key from `.env`, wired into the running process, documented in
the runbook, and proved by a test that measures a real `labelLogger()` child rather
than assuming winston propagates the level to children.
</objective>

<d12_reconciliation>
D-12 states: "Every AGT-04 event gets one `info` line, unconditionally. No new
config key, no runtime toggle."

This plan does not violate it, and the distinction is load-bearing rather than
lawyerly. D-12 forbids a switch that *gates whether the AGT-04 event lines are
emitted* — those lines stay unconditional `.info()` calls in code (plan 07-05).
What this plan changes is the process-wide sink threshold, through the `LOG_LEVEL`
key that already exists and already governs every line this service writes. It adds
no new key and no per-feature toggle. Raising the threshold above `info` naturally
silences `info` lines, exactly as setting `LOG_LEVEL=warn` in the environment does
today — that is standard logging semantics, not a feature switch, and the code
emitting the lines remains unconditional either way.
</d12_reconciliation>

1. Create `src/ops/logLevelControl.ts`.

Export `reloadLogLevelFromEnvFile(envPath: string = path.resolve(process.cwd(), '.env')):
{ previous: string; current: string; changed: boolean; source: 'file' | 'env' | 'none' }`.
It reads the file with `fs.readFileSync` inside a `try`/`catch`, parses it with
`dotenv.parse` — NOT `dotenv.config`, because `parse` returns a plain object and
does not mutate `process.env`, and a signal handler must not silently rewrite the
process environment out from under code that already read it. Take only the
`LOG_LEVEL` key from the parsed object; when the file is unreadable or carries no
`LOG_LEVEL`, fall back to `process.env.LOG_LEVEL`; when neither supplies a value,
return `changed: false` with `source: 'none'` and emit one warn. Otherwise delegate
to `setLogLevel()` from Task 1 and return its result plus the source. Nothing in
this function may throw.

Export `registerLogLevelSignalHandler(signal: NodeJS.Signals = 'SIGHUP', envPath?: string): () => void`.
It builds a handler that calls `reloadLogLevelFromEnvFile(envPath)` inside a
`try`/`catch` and emits one `logger.warn` naming the previous and current level and
the signal that triggered it — at `warn` rather than `info` deliberately, so the
confirmation is visible even when the operator has the process pinned above `info`;
note in a comment that pinning above `warn` silences the confirmation itself.
Register it with `process.on(signal, handler)` and return a function that calls
`process.off(signal, handler)` so tests can unregister deterministically.

Use `SIGHUP` as the default and record why in a comment: `SIGUSR2` is claimed by
common Node tooling (PM2's log reopening, nodemon's restart), so binding the level
reload to it would collide with the deployment's own signal use. An unhandled
SIGHUP terminates the process by default, which is exactly why registering a
handler for it is safe once and only once, at startup.

without a restart — so the mechanism is discoverable from the log the operator is
already reading. Do not change the existing `SIGTERM`/`SIGINT` shutdown handlers.

3. Extend `test/log-level-runtime.test.ts` with a second `describe` covering all

rather than `'SIGHUP'` for the handler-registration cases so the test can never
interfere with the runner's own signal handling, and always call the returned
unregister function in `afterEach`. Assert explicitly that a key present only in
the temporary env file is still `undefined` on `process.env` after the reload.

4. Add section 11 to `docs/OPS-RUNBOOK.md`, titled for changing the log level
without a redeploy. Document: edit `LOG_LEVEL` in the deployed `.env`; send the
signal with `pm2 sendSignal SIGHUP <app-name>` or `kill -HUP <pid>` (and
`docker kill --signal=HUP <container>` for the Docker deployment); the accepted

running level unchanged with one warn; the confirmation line is written at `warn`;
and the change is in-memory only, so a process restart returns to whatever `.env`
holds at that moment. Cross-reference section 3's environment table for `LOG_LEVEL`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| OS signal -> process | Only a local user with permission to signal the process can trigger a reload. No network surface is added. |
| `.env` file -> process | The deployed environment file is read at reload time; it already holds the service's secrets and is already trusted at startup. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-07-06 | Elevation of Privilege | log-level reload surface | low | mitigate | The control is a POSIX signal, not an HTTP endpoint — it requires local process-signalling permission, so no authentication surface, route or allow-list is introduced. Deliberately chosen over an admin endpoint for exactly this reason. |
| T-07-07 | Denial of Service (disk) | raised level flooding the log | low | accept | A local operator can already do this by editing `.env` and restarting. The existing daily-rotate transport caps volume at 20 MB per file and 14 days, so the blast radius is unchanged from today. |
| T-07-08 | Information Disclosure | `.env` parsing | low | mitigate | Only the `LOG_LEVEL` key is read from the parsed object; no other key and no file content is logged. `dotenv.parse` is used rather than `dotenv.config` so `process.env` is never mutated by the reload. |
| T-07-09 | Denial of Service (availability) | signal handler | medium | mitigate | The handler is fully wrapped in try/catch and `setLogLevel` never throws, so a malformed `.env` cannot terminate the service. Registering a SIGHUP handler also removes the default terminate-on-SIGHUP behaviour, which is a net availability improvement. |
| T-07-SC-02 | Tampering (supply chain) | npm install surface | low | accept | This plan installs zero packages; `dotenv`, `fs` and `path` are already dependencies of this service. |
</threat_model>
