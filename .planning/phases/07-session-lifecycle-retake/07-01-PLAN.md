<assumption_delta_decision>
## Assumption delta: completion identity

The assumption-delta detector fired on the ROADMAP phrase *"The second could only
succeed if…"*. That literal match is a **false positive** — "second" there names a
duplicate event, not a second platform, tenant or auth method. The underlying
question it asks is nevertheless the centre of this phase, so it is answered here
rather than dismissed.

- **Primary noun:** the job, identified by `jobId`.
- **Delta:** completion identity has been **positional** — `completeInProgressJob()`
  (`localStore.ts:220-229`) selects `WHERE status='in_progress' ORDER BY
  acknowledged_at DESC LIMIT 1`, i.e. "whichever job is currently most-recently
  acknowledged". This phase moves it to **jobId-scoped**.
- **Decision: `promote`.** A jobId-scoped `completeJob(jobId, completedAt)` becomes
  the primary and only completion path, and the positional selection is **removed**,
  not kept alongside. `07-PATTERNS.md` maps `failJob()` (`localStore.ts:263-267`) as
  the id-scoped template and `claimNotification()` (`localStore.ts:474-481`) as the
  changes-count-returning template.
- **Rationale:** keeping the positional method alongside the scoped one leaves the
  unscoped path reachable by any caller that forgets to pass an id — which is
  precisely the SC-2 failure, re-armed.
- **Companion invariant:** Task 2 adds an assertion that `LocalStore.prototype`
  carries no positional completion method. It goes red the instant a future phase
  reintroduces the positional assumption.
</assumption_delta_decision>

<sc2_reconciliation>
## How SC-2 is proven — the two halves, and why neither alone is enough

ROADMAP criterion 2 demands that A's `session_end` can never complete B, **"proven
with a queued second guest, not reasoned about."** A reader arriving at
`test/queue-dual-completion.test.ts` will find it built on a hand-rolled mocked
`LocalStore`, and the obvious objection is that a mocked store can be made to
report anything. That objection is answered here, in writing, so nobody has to
re-derive the argument from RESEARCH.md's Validation Architecture section later.

**What the mocked-store test genuinely proves, and it is not small.** It is not a
stub of `completeJob` asserted against itself, and it is not a single-job
assertion. Two jobs are queued. Both are announced, dispatched and acknowledged
through the **real** `QueueService` dispatch path, with real timers advanced by
`vi.advanceTimersByTime()`. The stray second `session_end` is delivered through the
real `onAgentEvent()` entry point. What the mock replaces is only the SQLite
handle; every line of decision logic under test — which job the composite is
attributed to, which id `sessionEnded()` reads, whether `tick()` announces the next
guest — is the production code path. This is the same seam
`test/queue-countdown.test.ts` has used since Phase 2 to prove booth-state
sequencing, and it is what makes a two-guest scenario expressible at all: the real
store has no way to hold two dispatched guests without also running ingestion.

**What it does not prove.** A mocked `completeJob(jobId)` returns whatever the mock
decides. It cannot demonstrate that the *SQL* is scoped — that the trailing
`AND status = 'in_progress'` predicate is what makes a duplicate completion match
zero rows, and that a scoped `WHERE id = ?` cannot reach a second row. Those are
properties of the statement, not of the service.

**The companion closes exactly that gap.** Task 1 step 13 adds a block to
`test/local-store-persistence.test.ts` that opens a real temp-file database, writes
two real `queue_job` rows, drives both to `in_progress`, and asserts against the
real statement: `completeJob(A)` returns true once and false on repeat, guest B's
row is still `in_progress` afterwards, and no ordering or `LIMIT` appears in the
path. Same guarantee, opposite end of the stack, real rows.

**Together they discharge the bar.** The service-level test proves the right job id
reaches the store under a genuinely queued second guest; the store-level test proves
that id is the only row the SQL can touch. Neither is a substitute for the other,
and the phase would be under-proven with either one alone. The non-vacuity step in
`<verification>` removes the `AND status = 'in_progress'` predicate and requires
both to be observed failing, which is what stops this pair from being an argument
about tests rather than a test.
</sc2_reconciliation>
