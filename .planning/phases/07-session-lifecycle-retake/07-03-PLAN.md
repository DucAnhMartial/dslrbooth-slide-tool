<objective>
Replace the in-memory `printUploadSeen` Set with a durable pending-print registry
in SQLite, and move the `No print upload seen` warning off `session_end` and onto
registry expiry.

Purpose: the warning currently fires on every successful session, because
dslrBooth delivers the composite about one second after `session_end` (WINDOWS 9,
measured on job `BZWCWFN6`) while the evidence file shows the print upload arriving
26 seconds *before* it on another session. The ordering is not fixed, so an
immediate check cannot be right — SC-4 needs a settle window, not a faster check.
The registry also closes the hazard D-04's drop rule would otherwise create: without
it, "no dispatched session, so drop" would swallow a real guest's photo in exactly
the `BZWCWFN6` ordering.

Output: a `pending_print` table with its accessors, the completion path opening a
slot at the composite anchor, `onFileUpload` resolving against that slot, and a
sweep that warns once when a print genuinely never arrives.
</objective>

<flagged_assumption>
## RESEARCH.md Pitfall 3 — surfaced, not dropped

The registry is keyed by the jobId the Agent stamped on the print-composite event.
The Agent never clears `activeJobId` (D-05 leaves that defect in place
deliberately), so a print upload arriving *after* a third guest has been
acknowledged would carry that third guest's id and miss the original guest's
registry row — falling through to D-04's drop rule and losing a real photo, or in
the worst ordering matching a different guest's open slot.

The expiry value chosen below narrows this window; it does not close it. This is
the honest cost of D-05's Agent-untouched constraint, not a planning oversight, and
D-06's mismatch warn (plan 07-01) is what will tell anyone whether it is still
firing in production. Deferred idea "clear `activeJobId` in the Agent" is the real
fix and belongs to a future phase that opens that repository for another reason.
</flagged_assumption>

  <name>Task 0: Decision — pending-print registry schema and expiry default (one-way)</name>
  <decision>The pending-print registry's table name, column shape, status vocabulary, and expiry default</decision>
  <context>
D-08 is locked: the registry lives in SQLite, in its own table, not folded into
`notification_record`. What is Claude's discretion — and what this checkpoint asks
you to confirm — is the concrete shape, because it is a **one-way** decision. The
table ships into a live SQLite database that carries operational data only the
operator may delete, and this project's migration policy is additive-only: renaming
the table or a column later needs a data migration, not an edit.

The proposed shape, and why:

Table `pending_print`, matching `notification_record`'s naming register. Columns:
`jobId TEXT PRIMARY KEY`, `composite_path TEXT`, `status TEXT NOT NULL DEFAULT 'awaiting'`,
`opened_at INTEGER NOT NULL`, `expires_at INTEGER NOT NULL`, `resolved_at INTEGER`,
`updated_at TEXT NOT NULL DEFAULT 'now'`. The status vocabulary is exactly three
words: `awaiting`, `resolved`, `expired`.

An expired row is **marked, never deleted**. That is what lets the service tell
D-11's late-but-legitimate print (a row exists, expired) apart from D-04's
out-of-session photo (no row was ever opened). Deleting expired rows would collapse
those two cases into one and make it impossible to honour both decisions.

Expiry default `PENDING_PRINT_EXPIRY_MS = 600000` (10 minutes). RESEARCH.md's
assumption A2 derives the floor: the window must comfortably exceed
`NEXT_GUEST_COUNTDOWN_MS + SESSION_TIMEOUT_MS`, today 7000 + 300000 = 307000 ms, or
a legitimately late print could expire before the next guest could even physically
be dispatched. 600000 is roughly twice that floor and still bounded enough that the
`No print upload seen` warning arrives within the same event, not the next day.
  </context>
  <options>
    <option id="option-a">
      <name>Accept the proposed shape as written</name>
      <pros>Matches the existing naming register and the claim-lease/expiry column shape of `notification_record`; the three-word status keeps D-04 and D-11 distinguishable structurally; the expiry default is justified against measured numbers.</pros>
      <cons>Ten minutes is a long time to wait for the no-print warning on a booth that is genuinely misconfigured.</cons>
    </option>
    <option id="option-b">
      <name>Same shape, shorter expiry (e.g. 330000 ms, just above the derived floor)</name>
      <pros>The no-print warning arrives roughly five and a half minutes sooner.</pros>
      <cons>Sits barely above A2's floor, so any future increase to `SESSION_TIMEOUT_MS` or the countdown silently makes the expiry unsafe and starts dropping legitimate late prints.</cons>
    </option>
    <option id="option-c">
      <name>Different table or column names</name>
      <pros>Operator preference; the value is only a name.</pros>
      <cons>Must be decided now — renaming after the table ships into the live database requires a data migration under the additive-only policy.</cons>
    </option>
  </options>
  <resume-signal>Select: option-a, option-b, or option-c (with the names you want)</resume-signal>
  <reversibility rating="one-way">A new table in a live SQLite database under an additive-only migration policy; renaming or reshaping after it ships needs a data migration, and rows written in the meantime carry the old shape.</reversibility>
