<objective>
Write the operator contract for everything Phase 3 changed, and close the phase behind an
explicit human acceptance of the one-way cutover.

Purpose: D-05 requires the deployment consequence to be stated plainly in
`mirror-request/docs/OPS-RUNBOOK.md`, beside the webhook signing contract that already lives
there as §1. This is the second published integration contract this service owns, and unlike the
first it has a live counterparty: `dslrbooth-agent` now has its own git history and its own
deploy artifact, so a server release that is not paired with an Agent release takes the booth
out of service completely. Nobody discovers that from reading the code.

cross-repo integration harness, and research found no staging environment referenced anywhere in
`OPS-RUNBOOK.md` or `config.ts`. The two halves of the auth contract have each been proven
against their own side of the wire; that they meet correctly is a claim a human confirms, or
explicitly accepts the risk of, before the next production deploy.

repositories.

  <action>
1. Append a new `## 7. Agent WebSocket auth contract (`/agent`)` section to
   `mirror-request/docs/OPS-RUNBOOK.md`, after §6 and in the file's established voice: concrete
   headers and copy-pasteable commands, tables over prose, and absences stated outright rather
   than glossed. Do not restructure or renumber anything above it.

2. **The contract itself.** State that the Agent authenticates every WebSocket upgrade to
   `/agent` with an `Authorization` header carrying the `Bearer` scheme and the shared secret,
   that the server accepts the header form **only**, and that an upgrade failing verification is
   answered with a bare `HTTP/1.1 401 Unauthorized` on the raw socket and destroyed **before** the
   WebSocket handshake completes — so a rejected client never holds an open socket even briefly.
   Give the header as a small table in §1's style. Name both sides' variables: the server reads
   `AGENT_WS_TOKEN`, the Agent reads `EXTENSION_SERVICE_WS_TOKEN` alongside
   `EXTENSION_SERVICE_WS_URL`; they must hold the same secret. Add the two operational rules
   plainly: the secret never belongs in a URL, and this service never writes it to a log line at
   any level, including when rejecting — so "invalid or missing Authorization header" is all a
   rejection will ever tell you, by design.

3. **What breaks, and why.** State it as an outage, not a degradation: a server on this build
   rejects **every** connection from an Agent that has not been updated. The queue keeps accepting
   registrations and the booth simply stops being served — no `start_session` command reaches it.
   Mirror §1's framing: this is a published contract between two deployed components, implement
   and deploy it exactly.

   This section is the one place in the repository where the superseded query-string form may be
   written down, so that an operator debugging an old Agent recognises what they are looking at.
   Do not add any repository-wide negative search for that form to any gate — it legitimately
   lives here now.

4. **Deploy ordering.** Both components in the same maintenance window, never one and then the
   other later. Give the concrete sequence: build and deploy the server
   (`npm run build` in `mirror-request/`), and rebuild and deploy the Agent binary
   (`npm run build:exe` in `dslrbooth-agent/`, which produces `dslrbooth-agent.exe`). Note that
   unlike §1's webhook contract — where this service is the only implementation and no
   coordination is needed — this one genuinely has two parties, because `dslrbooth-agent` is now a
   separate repository with its own artifact.

5. **Verification before cutover, honestly scoped.** Give the fast, non-production checks as
   copy-pasteable commands in §4's style: `cd mirror-request && npx vitest run test/agent-auth.test.ts`
   and `cd dslrbooth-agent && npm test`. Then state the limitation plainly: those prove each side
   against its own expectations, not the two against each other. **There is no staging
   environment referenced anywhere in this repository's configuration or in this runbook.** Say
   that outright, in §2's voice ("no built-in retention job… as of Phase 1"), rather than
   implying a rehearsal tier exists. Describe the only rehearsal actually available: run the
   updated server locally, point an updated Agent build at it, and confirm it connects and
   receives a `start_session` command.

6. **Rollback.** Because the server accepts only the header form, rolling the server back while
   the Agent is already updated reproduces the identical outage in the opposite direction. State
   the rule in one line: roll back **both** or neither.

7. **What the operator will see in the logs.** A short table of the lines Phase 3 added, quoted
   verbatim from the source as it now stands, with what each means:
   the upgrade rejection; the last-wins displacement warning naming both connection ids (two
   Agents pointed at one server — a misconfiguration, and the flap is now visible instead of
   silent); the heartbeat timeout warning; the dispatch-skip line when no Agent is connected
   (which appears **once per outage**, not once per tick, so its absence during a long outage is
   correct, not a lost log); and the requeue-after-disconnect line.

   Close with the one fact an operator would otherwise misread, and tie it to §6: a requeue
   caused by the Agent disconnecting or being absent **does not increment `retries` and records
   no `stall_reason`**. A job that has bounced back to `queued` with a flat retry count and an
   empty stall reason was not a bad job — it was a booth that was not there. That is deliberate:
   a booth-side fault must never spend the guest's retry budget, or a handful of outages would
   mark a perfectly valid registration `failed`. Session-side faults — an acknowledgement timeout
   or an Agent NAK — still charge a retry and still record a reason from §6's vocabulary, exactly
   as before.

8. Do not change any behavior and do not edit any file under `src/`. This task is documentation
   only. Do not attempt to touch `.env.example` — this sandbox denies access to `.env*` paths, so
   §7 must be self-contained on the variable names it mentions.
