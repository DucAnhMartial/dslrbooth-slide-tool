<objective>
Implement time-windowed duplicate detection for `POST /on-register`: identity by source `id`
first, falling back to email or phone, bounded by a configurable window, answering a duplicate
with the original job id and no new work.

Purpose: the existing `processed_id` table gives permanent id-based idempotency, which cannot
catch the real-world case D-02 targets — a guest double-submitting the form and the source
system minting a fresh `id` each time. That produces two queue jobs for one person.

Output: a `received_at` column plus `findDuplicateRegistration()` on `LocalStore`, the dedup
ladder in the receiver, and an HTTP + store-level test suite.

**Repository note:** all git operations must be run inside `mirror-request/`; the workspace
root is not a git repository.
</objective>

## Resolution of RESEARCH.md Open Question 2 (D-02 semantics)

RESEARCH.md flagged that D-02's wording — "prioritizes source `id`; if it is absent, use email
or phone number" — has two readings, and asked the planner to pick one explicitly rather than
leave it ambiguous in task text.

**Chosen reading:** "absent" means *an `id` match is absent*, not *the `id` field is absent*.
The dedup ladder is therefore: (1) look for a registration with the same `id` inside the
window; (2) if none, look for a registration with a matching non-empty `email` or non-empty
`phone` inside the window.

**Why:** the alternative reading requires relaxing the existing hard `400 {error:'id and name
are required'}` at `mirrorReceiver.ts:30-32`, which is input validation this phase was not
asked to weaken (ASVS V5) and which no locked decision asks to change. Under that reading the
fallback would also be dead code in practice, because a payload with no `id` never reaches the
dedup step. Under the chosen reading the fallback does the work D-02 exists for: catching a
resubmission that arrives with a freshly-minted `id`.

**Explicitly out of scope:** relaxing the `id`-required 400. If the developer intends genuinely
`id`-less payloads to be accepted, that is a new decision, not an implementation detail — it is
raised for confirmation in plan 01-05 task 3.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Authenticated webhook payload -> dedup query | Attacker-supplied `email`/`phone` values become SQL parameters and identity claims |
| Incoming registration -> existing persisted registration | A new request can cause an existing guest's record to be read out, or overwritten if the duplicate path is wrong |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-22 | Tampering | SQL injection through `email` / `phone` in the dedup query | high | mitigate | `better-sqlite3` prepared statements with `?` placeholders only; no string interpolation into SQL (task 1) |
| T-01-23 | Tampering | duplicate path overwrites the original registration and nulls its stored raw payload | high | mitigate | The duplicate branch returns before every persistence call; grep gate asserts a single `upsertRegistration` call site (task 2, RESEARCH.md Pitfall 7) |
| T-01-24 | Spoofing | an attacker submits a blank-contact payload and is merged into another guest's registration | high | mitigate | The `? <> ''` guards mean empty email and empty phone can never match; covered by a dedicated test (task 1) |
| T-01-25 | Information Disclosure | the duplicate response leaks another guest's job id to whoever submitted the second request | medium | accept | The endpoint is already authenticated by HMAC and IP allow-list, so the caller is Mirror Request itself, not a guest browser; D-03 explicitly requires echoing the original job id. Revisit if `/on-register` is ever exposed to end users. |
| T-01-26 | Information Disclosure | the dedup log line leaks guest email or phone | medium | mitigate | The log line names ids only and passes a plain string, so Winston's printf masking applies as a second layer (task 2) |

| T-01-SC | Tampering | npm/pip/cargo installs | high | mitigate | No package installs in this plan; RESEARCH.md `## Package Legitimacy Audit` covers the only two Phase 1 packages, both verdict OK / Approved |
