<objective>
Prove, end to end and against live data, that the exact projection which will
become `photobooth.registrations` carries a real `ets_web` registration all the
way into the Extension Service's SQLite queue — before any DDL touches
production.

Purpose: this phase's central risk is that the DDL is written, applied to a live
MySQL server, and only then discovered to be wrong — at which point the failure
is silent (Pitfall 1 lands inside `dbPoller`'s warn-and-retry catch and repeats
forever, every 3 seconds, with no guest ever reaching the booth). The tracer
inverts that order: the projection is executed read-only, its rows are bound
through the real `better-sqlite3` code path that has **never once executed** in
this project's history, and every claim the later plans depend on is measured
rather than assumed.

Output: one shared SQL declaration, one runnable read-only verification harness,
the committed DDL text, and two automated regressions.
</objective>

## Correction to CONTEXT.md D-03 — recorded so a later reader is not misled

D-03 states that the bare `INNER JOIN` on `event_manager_attendance.ticket_id =
ticketing_ticket.id` is, by itself, both the timestamp source and the validity
filter, and that "a cancelled or unconfirmed ticket is structurally incapable of
producing a VIEW row."

**The validity half holds. The 1:1 half does not.** `Attendance`'s uniqueness
constraint upstream is `(ticket, session)`, not `ticket`
(`/opt/web-ticket/qrcode/ets_web/apps/event_manager/models.py:719-726`), and
`Attendance.ticket` is a plain `ForeignKey`, not a `OneToOneField`
(`models.py:665-684`). `create_attendance_and_notify()` creates one row per
registered session (`event_manager/services/registration.py:196-239`), so a
ticket registered for N sessions yields N attendance rows and a bare join
duplicates that guest into the booth queue.

Today's data is safe only because all 27 `ticketing_orderdetail.registered_session`
values happen to be single-element arrays — a property of this event's
configuration, not a database constraint. **The projection therefore
de-duplicates explicitly** (`ROW_NUMBER() OVER (PARTITION BY t.id ORDER BY
a.created_at ASC, a.id ASC)`, keeping `rn = 1`), and Task 1's harness measures
the dedup against an independently-computed control rather than asserting it.

A second, lower-severity upstream finding is recorded here for the runbook (plan
06-06) and is **not** compensable by the projection: `register_ticket_to_event()`
commits `ticket.status = VALID` before calling `create_attendance_and_notify()`,
outside that method's atomic block (`registration.py:274-296`), so a
misconfigured event can leave a VALID ticket with **zero** attendance rows. That
is a miss, not a duplicate — the projection cannot see a row that does not exist.
</correction_to_context>
