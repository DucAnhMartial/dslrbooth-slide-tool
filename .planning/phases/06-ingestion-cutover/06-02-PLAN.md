<objective>
Make a broken ingestion seam loud, early, and non-fatal — and give D-05's
name-fallback warning the only home it can have now that `dbPoller.ts` is closed
to edits.

Purpose: the VIEW couples silently to `ets_web`'s table and column names. An
upstream migration breaks ingestion on the photobooth side with no signal to
whoever ran it, and the moment that matters most is a restart in the middle of a
live event. D-09 therefore inverts `config.ts`'s production fail-fast posture:
the probe alerts and the service keeps serving everyone already queued.

Output: a probe that distinguishes a broken VIEW from an unreachable database, a
pure name-source audit that satisfies D-05 without touching the ingestion path,
and the wiring that starts and stops both.
</objective>

<departures_from_research>
## Two deliberate departures, named so a reviewer does not read them as oversights

**1. The probe owns its own `mysql2` pool.** RESEARCH's code example and PATTERNS
both say the probe must reuse the pool `dbPoller.ts` already constructs and must
not create a second one. That is not reachable: `DBPoller.pool` is private, it is
created inside `start()`, and **D-02 forbids modifying `dbPoller.ts`** — including
adding an accessor. The probe therefore creates its own pool with
`connectionLimit: 1`, using the same lazy `require('mysql2/promise')` shape and
the same degrade-to-a-warn behaviour as `dbPoller.ts:43-63`. Cost: one additional
idle MySQL connection. Benefit: `dbPoller.ts` stays byte-identical, and the
probe is drivable by the identical `vi.spyOn(mysql2Promise, 'createPool')`
harness the poller's own tests already use.

**2. D-09's never-block posture is a departure from `config.ts`, by design.**
`config.ts:65-77` throws at startup when a production control is unconfigured.
The probe does the opposite: every failure path logs and returns. That contrast
is the decision, not an inconsistency — refusing to start converts an ingestion
outage into a total outage for the queue, booth, display and notifications of
everyone already in line.

**3. D-05's warn is emitted on the probe's cadence, not at ingest.** PATTERNS
flagged that D-05's "one warn per fall-through" has nowhere to live, since the
fallback chain is computed in SQL and `dbPoller.ts` may not be touched, and
suggested treating the synthetic label plus a runbook note as sufficient. That
would be a silent reduction of a locked decision. Instead the projection carries
a `name_source` column on a **separate** view (`photobooth.registrations_name_audit`,
plan 06-01) — leaving `photobooth.registrations` at exactly the six columns
CONTEXT's discretion clause requires — and the probe emits the warn. The only
honest difference from the literal decision is latency: the warn appears within
one `VIEW_PROBE_INTERVAL_MS` of the guest, not at the instant of ingest. Name
that latency in the runbook.
</departures_from_research>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| `ets_web` schema -> `photobooth` VIEW | An upstream migration can invalidate the view at any time with no signal on this side |
| Extension Service -> `NOTIFY_WEBHOOK_URL` receiver | An outbound POST to a third-party process (`web-slide`), which performs no lookup and renders what it is given |
| Probe -> log files | New log surfaces are new opportunities for PII to escape masking (AUTH-03) |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
