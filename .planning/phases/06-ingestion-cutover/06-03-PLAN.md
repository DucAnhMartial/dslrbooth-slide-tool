<objective>
Close the residual D-10 opened: `registrations.id` becomes `ticket_code`, which
is CSPRNG-minted but only **40 bits** wide — enumerable by an unthrottled
attacker against an endpoint that deliberately returns 200 for a valid foreign
id, because holding the id *is* the authorisation.

Purpose: rate limiting is the compensating control that makes the shipped
capability-URL design sound at this entropy level. Widening the id would require
changing `ets_web`, which the human's hard constraint forbids absolutely.

Output: a hand-rolled, Express-agnostic, bounded limiter mounted ahead of the
`/status/:jobId` handler, and a test suite that proves both that it throttles and
that throttling tells an attacker nothing about which ids are real.
</objective>

<why_no_dependency>
RESEARCH ran this project's package-legitimacy gate on the one obvious candidate.
`express-rate-limit` returned `[SUS]` with `reasons: ["too-new"]` — almost
certainly a false positive (a patch release of a package with 57.8M weekly
downloads and a dedicated GitHub org), but the gate is mechanical and a `[SUS]`
verdict requires a blocking human checkpoint before install. That is
disproportionate for what a small `Map`-based limiter achieves, and this project
has added no runtime dependency since Phase 1. `ipAllowlist.ts` is the
established template: plain exported functions, no class, no framework coupling
in the core decision, structurally typed parameters so the logic is unit-testable
without booting Express.
</why_no_dependency>

functions plus one small factory, no class holding hidden state, and a header

`RateLimitState` is `{ entries: Map<string, { windowStart: number; count: number }> }`.
`createRateLimitState()` returns a fresh one. `checkRateLimit(key, now, state, opts)`
reads the entry, resets it when `now - windowStart >= opts.windowMs`, increments,
writes back, and returns `{ limited: count > opts.max, count }`. It takes `now`
as a parameter and never calls `Date.now()` itself — the same injectability rule
every timing knob in this project has followed since Phase 2.

`pruneExpired(state, now, windowMs, maxKeys)` deletes every entry whose window
has closed; if the map is still above `maxKeys` afterwards it deletes entries in
ascending `windowStart` order until it is at `maxKeys`, i.e. the oldest windows
go first. Returns the number removed. Call it from the middleware whenever
`state.entries.size` exceeds `maxKeys`, so the common path stays O(1) and the
sweep is amortised.

`createStatusRateLimiter(opts)` returns an Express middleware `(req, res, next)`
that derives the key with `clientIp(req)` imported from `./ipAllowlist` — do not
re-derive an address a second way; two derivations are two definitions of "a
client" free to drift apart, and `ipAllowlist.ts`'s header already explains why
`req.ip` is the direct TCP peer here. Fall back to the literal `unknown` when the
derived address is empty, so a keyless request shares one bucket instead of
bypassing the limiter. On `limited`, respond
`res.status(RATE_LIMITED_STATUS).json(RATE_LIMITED_BODY)` and do not call
`next()`. Otherwise call `next()`. `opts` carries `windowMs`, `max`, `maxKeys`,
an optional injected `state`, and an optional injected `now: () => number`,
defaulting to `Date.now` — so tests drive both time and state through the
constructor rather than through module-level mutation.

`RATE_LIMITED_BODY` is exactly `{ error: 'too many requests' }` — one key, no
`reason`, `code`, `hint`, `detail` or retry field, and no `Retry-After` header.
Follow `statusRoute.ts:8-21`'s reasoning verbatim: two response shapes are two
failure modes waiting to drift apart, and any difference between them is an
enumeration oracle.

Create `test/status-rate-limit.test.ts` and cover every behaviour above against
the pure functions directly, driving `now` as a plain number.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Public internet -> `GET /status/:jobId` | Unauthenticated by design: the jobId is the capability. No IP allow-list is possible — a guest's phone is not on the room LAN |
| Client address -> limiter key | `req.ip` is the direct TCP peer; no application-level proxy trust is configured anywhere in this service |
| Limiter state -> process memory | An attacker rotating source addresses controls how many map entries exist |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-06-01 | Spoofing / Information Disclosure | `GET /status/:jobId` against a 40-bit `ticket_code` | high | mitigate | Fixed-window limiter, default 30 requests per 60s per client address, mounted as the first handler on the route |
| T-06-02 | Information Disclosure | The throttled response | high | mitigate | Status 429 with the single-key body `{ error: 'too many requests' }` for every caller, and the limiter gates ahead of `store.getJob()` so the real-id path does no extra work before refusal — proved by a call-count assertion, not by timing |
| T-06-06 | Denial of Service | The in-memory limiter map | medium | mitigate | `pruneExpired` plus a `STATUS_RATE_LIMIT_MAX_KEYS` cap with oldest-window-first eviction; asserted by pushing twice `maxKeys` distinct keys through the middleware |
| T-06-12 | Spoofing | Distributed enumeration from many source addresses | medium | accept | A per-address limiter cannot stop a distributed walk of a 2^40 space. Closing that requires a wider id, which needs an `ets_web` code change the human has forbidden absolutely.
