<objective>
Close the gap the live booth run on 2026-08-18 11:23 exposed: the first `session_start`
of a dispatched session is forwarded by the Agent with `jobId: undefined`, so the server
silently drops it, `attempt_no` never reaches 1, the retake is not recognised as a retake,
and the grace window finalises the guest's job on the DISCARDED photo.

This is Phase 11's own must-have BTH-01/NOT-01 failing in production. Fix it in both
places: the server stops depending on an Agent-supplied id it already knows, and the Agent
stops emitting triggers before it has stamped the id.
</objective>

<evidence>
Agent log, booth PC, 2026-08-18 (agent clock):

    11:22:53.907  Trigger received: session_start {"param1":"PrintOnly"}

`dslrbooth-agent/src/commands.ts` calls `deps.setActiveJobId(jobId)` only AFTER

<task number="1" name="Server: the booth binding is the authority for session_start">
The server dispatched the job and wrote `current_job_id` at dispatch time
(`setBoothBusy`). It does not need the Agent to tell it which job a `session_start`
belongs to when the booth is already bound.

In `onAgentEvent`, resolve the effective job for `session_start` as
`jobId ?? this.store.getBoothCurrentJobId()` and pass that to
`sessionAckedFromEvent`. When BOTH are absent, log exactly one line saying a
`session_start` arrived with no job id and no booth binding, and do nothing —
preserving D-06's stray-session_start guard.

Keep `sessionAckedFromEvent`'s internal logic unchanged: an Agent-supplied id that
DISAGREES with the binding must still hit the existing mismatch guard. The fallback
applies only when the Agent supplied nothing.

Write `test/queue-first-session-start-race.test.ts` replaying the measured race
verbatim: dispatch, `session_start` with `jobId: undefined` 20ms later, then the
full sequence through the retake, and assert `attempt_no` reaches 1 on the FIRST
session_start and 2 on the retake, that the grace timer is cancelled, and that the
notification carries attempt 2's URL.

Commit: fix(11-06): the booth binding answers session_start when the Agent cannot
</task>

<task number="2" name="Agent: stamp the job id before the session can start">

`await deps.dslrBooth.startSession(mode)`, and clear it (`setActiveJobId(undefined)`)
on the failure branch so a failed start cannot leave a stale id stamped on later
triggers.

Add `test/command-active-job-id.test.ts` proving: the id is set before
`startSession` is awaited (assert ordering, e.g. by having the `startSession` stub
read back the current value), and that it is cleared when the API reports failure.

Run the agent suite. Do NOT rebuild the Windows installer — packaging and
redeployment to booth PCs is the operator's step, noted in the summary.
