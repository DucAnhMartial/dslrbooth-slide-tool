# Phase 999.1 Research: Slide caption config

## Locked decisions and deferred work (verbatim)

### Caption content and safety

- **D999.1-01:** `guestNameTemplate` defaults to `{guest_name}`. Replace every
  literal `{guest_name}` with the guest name; a template without that token is
  valid and produces a fixed per-event sentence.
- **D999.1-02:** Caption text is always inserted with `textContent`, never by
  interpolating into `innerHTML`. The safe render shape is
  `name.textContent = template.replace(/\{guest_name\}/g, photo.name || '')`.
- **D999.1-03:** A long resulting caption may wrap to at most two lines; any
  remaining content is ellipsized. This is the operator's explicit choice.
- **D999.1-04:** Keep the caption as one uniform style. Per-name emphasis
  (such as bold guest names) is out of scope.

### Caption placement and photo fitting

- **D999.1-05:** `captionPosition` defaults to `bottom-left` and offers a
  9-point grid anchored to the photo's own box, never to the full stage. The
  image must therefore be inside a shrink-to-fit wrapper.
- **D999.1-06:** `photoFit` defaults to `contain`, preserving all current
  rendering. `cover` fills the screen and may crop the photo; the CMS must
  plainly warn that it is intended for landscape frames and can remove event
  logos or most of a portrait strip.
- **D999.1-07:** Under `cover`, the photo box is the stage, so the caption
  remains over the photo. Derive the dark legibility gradient from the chosen
  caption position; no separate gradient configuration field is added. A
  gradient is unnecessary when `contain` places the caption in a black bar.

### CMS and live display path

- **D999.1-08:** Follow the existing `idleHeading` configuration path end to
  end: `DEFAULT_EVENT_CONFIG`, SQLite mapping and allow-list, EventConfig
  types, additive `event` migration, CMS form, non-null validator, and live
  display projection.
- **D999.1-09:** Render the configuration in both
  `src/display/slidesPage.ts` and `src/display/displayPage.ts`; both surfaces
  already draw guest names and must not drift. — **Reversibility:** costly —
  the intentionally standalone page implementations require paired changes
  and cross-page regression coverage.

### Deferred Ideas

- Styling only the substituted guest name differently from the surrounding
  caption text (for example, bold) belongs in a later phase.

## Research findings

### Current architecture and exact seams

- `[code: mirror-request/src/state/localStore.ts:25-132]` `DEFAULT_EVENT_CONFIG` and the private `toEventConfig()` projection are the single default/coalescing seam. Add camel-case defaults `guestNameTemplate: '{guest_name}'`, `captionPosition: 'bottom-left'`, and `photoFit: 'contain'`; map their snake-case row fields with `??` defaults.
- `[code: mirror-request/src/types.ts:96-147]` `EventConfig` is the typed wire contract consumed by `DisplayServer` and both static page templates. The three fields must be non-null `string` union types (`captionPosition` and `photoFit` should be literal unions), not optional compatibility fields.
- `[code: mirror-request/src/state/localStore.ts:143-172, 292-333, 552-573, 1485-1497]` the event table, `EventRow`, `EVENT_UPDATABLE_COLUMNS`, and `migrate()` must be changed together. The established safe migration is one `PRAGMA table_info('event')` read followed by conditional additive `ALTER TABLE ... ADD COLUMN ... NOT NULL DEFAULT ...`; this makes existing rows display the old rendering immediately.
- `[code: mirror-request/src/cms/cmsEventPages.ts:470-538, 618-736]` the form derives visible “which screen” tags from `FIELD_SCREEN_MAP`; every new control needs an entry or its screen tag is blank. Add a capped template text field and two `<select>` fields, placing an unambiguous Vietnamese cropping warning next to `photo_fit`.
- `[code: mirror-request/src/cms/cmsEventRoutes.ts:66-178]` `FIELD_VALIDATORS` accepts only named fields, rejects an entire patch if a recognized value is invalid, and ignores unknown fields. Add `textField(FIELD_CAPS.guest_name_template)` and exact enum validators. Do not use the nullable `textField` result for the three new NOT NULL columns: it may return `null`, while `updateEvent()` converts nullish patch values to `NULL` and would cause a constraint failure. A non-null text validator must reject empty/non-string input (or explicitly substitute the default before creating the patch).
- `[code: mirror-request/src/display/displayServer.ts:175-208]` no display-server change beyond the expanded typed event projection is required: it calls `getActiveEventConfig()` afresh for every snapshot and its serialized-diff guard broadcasts a CMS update to connected displays without reload.
- `[code: mirror-request/src/display/slidesPage.ts:111-139, 264-322]` `shotTile(photo, badgeText)` is the only live photo-caption rendering seam. Today the `<img>` uses `object-fit:contain`, and the full-stage `.slide-overlay` anchors the name to the stage; replace this with a photo-frame wrapper and a caption element built with DOM APIs.

### Default-screen conflict requiring plan resolution

- `[code: mirror-request/src/display/displayPage.ts:330-484; test: mirror-request/test/display-default-view-regression.test.ts:49-103]` the default `/display-screen` intentionally renders **no photographs**, no `shotTile`, no slideshow, and no guest-name overlay. Its stage precedence is announcing → capturing → idle. This was explicitly locked by the existing regression test after the 2026-08-14 operator change.
- `[context: D999.1-09]` says both pages already draw guest names and need paired rendering. That premise is now false in the repository. The implementation plan must not silently reintroduce photographs/captions to `displayPage.ts`, as doing so violates its current product decision and regression pins.
- **Prescriptive resolution:** extend the config contract, CMS form, migration, and snapshot path once for both pages; implement visual caption/fit behaviour in `slidesPage.ts`; update `displayPage.ts` only for its explicit config-consumption/cross-page contract if required by the intended revised default-screen behaviour. If the operator truly wants the caption visible on the default screen, that is a scope change requiring a new default-screen photo-renderer decision and replacement of its no-photo regression tests.

### Recommended data and validation contract

Use snake_case only at the persistence/request boundary and camelCase only in `EventConfig`:

| Request/column | EventConfig | Allowed values | Default |
|---|---|---|---|
| `guest_name_template` | `guestNameTemplate` | non-empty trimmed text, capped | `{guest_name}` |
| `caption_position` | `captionPosition` | `top-left`, `top-center`, `top-right`, `middle-left`, `middle-center`, `middle-right`, `bottom-left`, `bottom-center`, `bottom-right` | `bottom-left` |
| `photo_fit` | `photoFit` | `contain`, `cover` | `contain` |

- `[decision: D999.1-01]` `guest_name_template` must preserve a template without `{guest_name}`; never validate for the token or append a name automatically.
- `[recommendation]` Set `FIELD_CAPS.guest_name_template` to 240 Unicode code units. It bounds database/wire/DOM payload while the two-line CSS rule, rather than an arbitrary low cap, owns the visible-length policy. Apply the cap after `trim()`, matching existing `textField()` behaviour.
- `[recommendation]` Make all three columns `TEXT NOT NULL DEFAULT ...` in both fresh schema and migration. For the text field, introduce `requiredTextField(cap, fallback?)` that refuses empty input; preserving the default is an explicit CMS action of submitting `{guest_name}`, not an accidental database error. This meets D999.1-08’s non-null-validator rule.

### Rendering design

1. In `shotTile`, read a fresh `cfg`-derived module-level state on every `render()` (as existing toggles do), with compatibility fallbacks for an old snapshot: `template = typeof cfg.guestNameTemplate === 'string' ? cfg.guestNameTemplate : '{guest_name}'`, `position = validPosition(cfg.captionPosition) ? cfg.captionPosition : 'bottom-left'`, and same for `photoFit` / `contain`.
2. Build a `.photo-frame` with `position:relative`; append its `<img>` and caption to it; append the frame to `.slide`. Never put the caption in stage-level `.slide-overlay`.
3. For `contain`, make the frame shrink to the rendered image (CSS grid overlay is a practical layout: image and caption occupy the same grid cell, with `max-width/max-height:100%`). This keeps a portrait strip’s caption beside/on its own visual box instead of a remote stage bar. Preserve `object-fit:contain` and the existing black stage.
4. For `cover`, give `.photo-frame` the stage bounds and use `img { width:100%; height:100%; object-fit:cover }`. The position then correctly means a stage corner/edge/centre because the photo box is the stage.
5. Apply a position class/data attribute such as `caption--bottom-left`; map the nine positions to `top|50%|bottom` and `left|50%|right`, using `transform` only for centre axes. Do not derive CSS selectors from unsanitised config strings; only assign a class after exact enum validation/fallback.
6. Render `name.textContent = template.replace(/\{guest_name\}/g, photo.name || '')`. Keep a single `<p>` with the existing uniform weight; do not create spans around substitutions.
7. Enforce D999.1-03 with `display:-webkit-box; -webkit-box-orient:vertical; -webkit-line-clamp:2; overflow:hidden;` plus a bounded caption width. `text-overflow:ellipsis` alone does not ellipsize multi-line text. Avoid `white-space:nowrap`, which contradicts the required two-line wrap.
8. For cover only, add directional dark gradient classes derived from the chosen position (bottom → `to top`, top → `to bottom`, left → `to right`, right → `to left`; centre can use a radial dark scrim). For contain, no gradient is needed because the caption’s frame-local position will land in black letterboxing when applicable. This is a rendering derivation, not persisted state.

### Security and correctness pitfalls

- `[decision: D999.1-02; code: slidesPage.ts:264-322]` Never use `innerHTML` for either template or guest name. Both are untrusted in the browser: CMS text can become stored XSS and guest data is external input. The existing broken-image markup is static and immediately assigns its message by `textContent`; it is not a precedent for interpolating caption text.
- `[code: cmsEventRoutes.ts:90-131]` Reject enum values rather than coercing them. Unknown position/fit values must make the entire CMS save return 400 and leave the event unchanged; accepting a CSS-like arbitrary string creates an injection/drift path.
- `[code: localStore.ts:1485-1497]` Never add request keys directly into SQL assignments. Add only literal names to `EVENT_UPDATABLE_COLUMNS`; the current allow-list and bound values prevent SQL injection.
- `[code: displayServer.ts:137-208]` Do not add raw `event_photo` or `queue_job` data to the display snapshot just to support captions. `{photoUrl, name}` already has the two values needed; keeping that narrow projection protects queue/operator fields.
- `[code: display-default-view-regression.test.ts:49-103]` Do not remove the no-photo test merely to make D999.1-09 appear satisfied. That would reverse a documented product decision without a new operator decision.
- `[browser-layout]` A stage-wide absolutely positioned overlay is the exact failure D999.1-05 identifies. A wrapper that is merely an `inset:0` stage is equally wrong for `contain`; test a portrait aspect ratio specifically.

### Verification strategy

Add focused coverage alongside the established suites, not a new untested rendering framework.

- `test/cms-event-config.test.ts`: assert the three named CMS controls, sensible screen tags, the cover cropping warning, defaults for a bare event, accepted exact enum values, invalid enum/type/empty template rejection, all-token replacement preservation at storage level, and atomic no-partial-write behaviour.
- `test/local-store-event-toggles.test.ts` (or a dedicated local-store config test): prove fresh schema defaults, migration of a pre-phase `event` table adds all three columns with non-null defaults, values round-trip through `getEventConfig()` / active projection, and a hand-edited null row falls back safely only if legacy compatibility is intentionally retained.
- `test/display-slides-view.test.ts`: source/HTML structural checks for `textContent` substitution with global `/\{guest_name\}/g`, no caption/template interpolation into `innerHTML`, default `contain`, a frame-local overlay, all nine explicit position tokens, two-line clamp CSS, and cover-specific `object-fit:cover` plus derived—not configured—gradient behaviour. Add a behavioural browser-level test only if a DOM-capable test harness already exists; Vitest’s current tests inspect the returned standalone HTML and snapshot data.
- `test/display-idle-default.test.ts` and `test/cms-event-tracer.test.ts`: extend “every projected non-null config field has a shipped default” assertions to prevent a new undefined value from reaching a TV.
- `test/cms-field-screen-tags.test.ts`: update the map only to match actual page dereferences. With the current default page no-photo design, all three controls should be `slides`, not `both`; mark a contrary desired tag as requiring the product-decision resolution above.
- `test/display-default-view-regression.test.ts`: keep the default-page no-photo/no-caption guard unless the operator explicitly changes that screen’s role. This is the paired cross-page regression required by the current repository state.

### Recommended implementation order

1. Establish the storage/type/validator contract and migration tests first; this is the live snapshot contract.
2. Add CMS controls, warning copy, field map, and route tests second; run full CMS config tests to confirm no null constraint path.
3. Change `slidesPage.ts` rendering and CSS with default-preservation and injection regression tests third.
4. Resolve and then test the `displayPage.ts` conflict explicitly; do not bundle a visual reintroduction of photos into an otherwise-config-only change.
