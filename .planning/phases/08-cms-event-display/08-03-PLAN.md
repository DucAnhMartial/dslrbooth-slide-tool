<objective>
Give the operator the console CMS-01 promises: create and edit a saved event with every
configurable field, upload its branding safely, and switch which event is live — with the D-02
warning that says how many guests are still waiting instead of hard-locking the CMS mid-event.

Purpose: this is the plan that makes "a new customer is a configuration change, not a deploy"
literally true, and it is also the plan that owns the exact upload surface CMS-05 documents as
the live hole `web-slide` had — anonymous 20MB writes into a statically-served directory with a
caller-chosen extension. That class closes here structurally.

Output: the upload receiving half, the event configuration form and list, and the active-event
switch with its guests-waiting confirmation.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator browser → `POST /cms/api/assets` | Arbitrary bytes and arbitrary declared metadata cross into the filesystem |
| operator browser → event configuration writes | Free-text and numeric values cross into what every TV in the room renders |
| CMS → `active_event` | A single-row write that changes every screen at once while guests may be mid-queue |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-08-13 | Tampering / EoP | `POST /cms/api/assets` content-type confusion | high | mitigate | Magic-byte sniff against exactly four signatures; the declared MIME and any client-supplied name are ignored entirely; SVG, HTML and JS are unreachable because they match no signature — this is the structural closure of the CMS-05 mechanism |
| T-08-14 | Tampering | path traversal via upload filename | high | mitigate | The stored name is minted from `randomUUID()` plus the sniffed extension; no client string is an input to the path, so traversal has no vector rather than a filtered one (D-15) |
| T-08-15 | Denial of Service | oversize or malformed base64 upload | medium | mitigate | Decoded length checked against `CMS_UPLOAD_MAX_BYTES` before any write; the route-scoped body limit from plan 08-01 bounds the request itself; failures return one generic shape and write nothing |
| T-08-16 | Tampering | unauthenticated upload | high | mitigate | The upload route sits behind both plan 08-01 layers — `CMS_IP_WHITELIST` then `requireSession()`; a test asserts an unauthenticated post writes no file |
| T-08-17 | Tampering | operator-supplied config rendered into room-screen markup | medium | mitigate | Text fields are length-capped and validated server-side; enumerated fields (font, layout) accept only known values; values are inserted as text content and CSS custom-property values, never as markup, and the room screen falls back to the system stack for an unknown font value |
| T-08-18 | Repudiation | an unnoticed active-event switch mid-event | low | accept | The switch is deliberately permitted with guests queued (D-02, written from a real incident where blocking would have hard-locked the CMS); the compensating control is the stated guests-waiting count plus explicit confirmation, and one masked log line per switch, not a block |
| T-08-SC | Tampering | npm installs | low | accept | Zero new packages — base64-in-JSON via the existing parser deliberately avoids `multer` and its recurring multipart-parser advisories; the four magic-byte signatures are hand-rolled deliberately as a closed-form check, not an open-ended parser |
</threat_model>
