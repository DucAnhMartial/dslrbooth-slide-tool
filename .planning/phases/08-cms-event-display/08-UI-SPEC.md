# Phase 8 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

## Scope note — two surfaces, one contract

This phase ships **two** UI surfaces, not one:

- **Room Screen** — the guest-facing TV display (replaces `web-slide/index.html` and Phase
  5's placeholder `displayPage.ts`). Viewed from meters away, portrait or landscape, **no
  interaction**. Driven by config (CMS-01) + the WS `/display` feed (SC-5).
- **CMS Console** — the operator's admin tool (CMS-01..05). Used on a laptop, sometimes
  mid-event under pressure, behind login (CMS-04).

Both surfaces are server-rendered inline HTML/CSS/vanilla-JS template strings served by
Express — the established in-repo pattern (`src/display/displayPage.ts`, `src/status/*`).
**No frontend framework, no build pipeline beyond `tsc`** — this is a locked decision
(ROADMAP, 2026-08-12), not a gap to fill with React/Vite.

Every table below is split Room Screen / CMS Console where the two surfaces differ.
Per CMS-01, several Room Screen properties (background, colors, font, idle image,
title/greeting, QR/CTA copy, photo count, per-photo duration, layout style) are
**event-configurable**, not fixed brand values. Where that applies, this contract declares
the **default** (what renders before any operator customizes anything, which UI-01 requires
to be correct on its own) and the **constraint envelope** the CMS's config form must enforce
so an operator can never configure the screen into an illegible or broken state.

## Design System

| Property | Value |
|----------|-------|
| Tool | none — not a React/Next.js/Vite project; shadcn gate does not apply (verified: no `components.json`, no `package.json` React/Vite/Next dependency, no `tailwind.config.*`; `package.json` is express+ws+better-sqlite3+winston, zero frontend deps) |
| Component library | none — vanilla DOM, server-rendered template-string HTML (matches `displayPage.ts`, `statusRoute.ts`'s sibling pages) |
| Icon library | none — hand-authored inline SVG only, ≤6 icons total across both surfaces (upload, trash/delete, check/success, warning/error, eye/preview, external-link). No icon font, no npm icon package — consistent with the zero-build-pipeline constraint. Room Screen QR code is a **generated image**, not a client-side icon (see QR/CTA below). **Accessibility contract (checker Dimension-2 FLAG, accepted): no icon-only control ships.** Every one of the ≤6 icons appears WITH a visible Vietnamese text label beside it (the CMS is an operator tool used mid-event under pressure — an ambiguous glyph compounds that risk); where layout genuinely cannot fit the visible label, the control carries `aria-label` + `title` with the same Vietnamese string as fallback, and the SVG itself is `aria-hidden="true"` so screen readers announce the label once. |
| Font | System-ui stack by default on both surfaces. Room Screen font is CMS-01-configurable from a small curated, **self-hosted** list bundled with the service (never a Google Fonts / CDN `<link>` — a live event cannot depend on venue wifi reaching a third-party font host). The curated list's actual contents are Claude's discretion at plan/build time — flagged as an open question below. |

## Spacing Scale

Declared values (must be multiples of 4), shared by both surfaces:

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | Icon gaps, inline padding, badge padding |
| sm | 8px | Compact element spacing, form field internal padding |
| md | 16px | Default element spacing, CMS card padding |
| lg | 24px | Section padding, CMS form section gaps |
| xl | 32px | Layout gaps, CMS page margins |
| 2xl | 48px | Major section breaks |
| 3xl | 64px | Page-level spacing, Room Screen outer safe margin baseline |

**Exceptions:**
- Room Screen outer margin is **fluid, not a fixed token**: `4.5vw` (matches the proven
  `displayPage.ts` and `web-slide/index.html` incumbents), because the screen's physical size
  and aspect (portrait/landscape TV) are unknown at build time. Treat `3xl`/64px as the
  reference-viewport anchor for that fluid value, not a literal pixel Room Screen ever uses.
- CMS interactive controls (buttons, upload targets, event-list rows) get a **44px minimum
  touch target**, even though the primary input is a laptop trackpad — the "operator mid-event
  under pressure" persona (hard fact 6) may be on a touchscreen laptop or tablet, and a missed
  tap during a live event is the failure mode this exists to prevent.

## Typography

Two independent typography systems — Room Screen (TV, fluid) and CMS Console (admin,
fixed px). Each independently satisfies Nyquist's 3-4 sizes / 2 weights rule.

### Room Screen (fluid `clamp()` — proven pattern, carried from `displayPage.ts`)

| Role | Size (clamp, reference-viewport anchor) | Weight | Line Height |
|------|------------------------------------------|--------|-------------|
| Caption | `clamp(0.75rem, 1vw, 1rem)` → anchor 16px | 400 | 1.4 |
| Label | `clamp(1rem, 1.6vw, 1.5rem)` → anchor 20px | 400 | 1.4 |
| Heading | `clamp(1.25rem, 2vw, 1.8rem)` → anchor 28px | 700 | 1.2 |
| Display (hero: guest name, idle headline) | `clamp(2.5rem, 8vw, 8rem)` → anchor 64-128px | 700 | 1.05 |

Only 2 weights on Room Screen: **400 regular** (body/labels/queue list) and **700 bold**
(hero name, headline, CTA emphasis). The incumbent `web-slide/index.html` uses 500/600 in a
few places (logo, badges) — collapse those onto 400 or 700 in the rebuild; do not carry a
third weight forward.

Vietnamese diacritics must render correctly at every size — verify the chosen system-ui
stack and any curated custom font actually cover Vietnamese glyph ranges (Đ, ơ, ư, and all
tone-mark combining diacritics) before approving a font for the curated list.

### CMS Console (fixed px — standard admin/dashboard sizing)

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 14px | 400 | 1.5 |
| Label | 16px | 400 | 1.5 |
| Heading | 20px | 600 | 1.2 |
| Display (page title) | 28px | 600 | 1.2 |

Only 2 weights on CMS: **400 regular** and **600 semibold**.

## Color

Two independent palettes. Room Screen's is the **default/fallback theme** — CMS-01 lets an
operator override specific roles per event; the roles that stay fixed regardless of event
branding are called out explicitly, because they carry operational meaning (hard fact 6:
"nobody yet" must never look like "broken," and neither may ever look like "connection
lost" or "Agent offline").

### Room Screen — default theme (tokenizes the incumbent `web-slide/index.html` palette, not discarding it)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#0a0a0f` | Stage background, body |
| Secondary (30%) | `#13131a` / `#1c1c26` | Header bar, sidebar, queue-item cards |
| Accent (10%) | `#6c8fff` | Live/on-air status dot, active queue-item border+tint, progress/countdown fill, "new photo" badge, QR frame border, primary CTA emphasis |
| Destructive / system-status | `#a33127` (fixed, non-configurable) | Agent-offline indicator, feed-disconnected banner — **never themeable**, so an event's branding can never accidentally hide an operational fault |
| System-status success (fixed, non-configurable) | `#34d399` | Agent-online / live indicator — **never themeable**, same rationale |

**CMS-01 configurable roles:** Dominant/background, Secondary/surface, Accent, primary text
color, muted text color. **Not configurable:** the two system-status colors above.

Accent reserved for: live/on-air status dot, active queue-item border and background tint,
progress-bar/countdown fill, "new photo" badge, QR/CTA frame border, primary CTA button
background. Never applied to body text, never applied to more than one element type per
screen state at a time (no "everything glows" drift).

### CMS Console — fixed admin palette (not event-configurable; this is the operator's own tool)

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#f7f7f9` | Page background |
| Secondary (30%) | `#ffffff` (+ `rgba(0,0,0,.08)` border) | Cards, panels, nav, form containers |
| Accent (10%) | `#6c8fff` | Primary CTA buttons ("Lưu cấu hình", "Đăng nhập", "Tạo sự kiện mới"), active nav item, focus rings, links — shared hex with Room Screen's accent for one visual system across both surfaces |
| Destructive | `#a33127` (shared with Room Screen's fixed error red — one destructive language across the product) | Delete event, clear photo history, log out confirmation emphasis |

Accent reserved for: primary CTA buttons, active nav/tab state, input focus ring, links.
Never applied to body text or table rows.

## Copywriting Contract

All copy is Vietnamese (hard fact 8), matching the existing tone already proven in
`displayPage.ts` / `web-slide/index.html` (direct, present-tense, short). Split into
**CMS system copy** (fixed, ships with the product) and **Room Screen default copy**
(CMS-01-editable per event — the values below are what a *new, uncustomized* event shows,
which is what makes UI-01 hold for every future event, not just the very first boot).

### CMS system copy (fixed — not per-event)

| Element | Copy |
|---------|------|
| Primary CTA — save config | "Lưu cấu hình" |
| Primary CTA — login | "Đăng nhập" |
| Primary CTA — new event | "+ Tạo sự kiện mới" |
| Primary CTA — test Agent connection (UI-02) | "Kiểm tra kết nối" |
| Save success | "Đã lưu cấu hình sự kiện" |
| Save error | "Không lưu được cấu hình — vui lòng thử lại. Nếu vẫn lỗi, liên hệ kỹ thuật." |
| Agent connection test — success | "Kết nối Agent thành công" |
| Agent connection test — failure | "Không kết nối được Agent — kiểm tra lại thông tin." |
| Login error | "Sai tên đăng nhập hoặc mật khẩu. Vui lòng thử lại." |
| Empty state — event list heading | "Chưa có sự kiện nào" |
| Empty state — event list body | "Tạo sự kiện đầu tiên để bắt đầu cấu hình màn hình phòng." |
| Empty state — photo history heading | "Chưa có ảnh nào" |
| Empty state — photo history body | "Ảnh sẽ xuất hiện tại đây ngay khi khách đầu tiên chụp xong." |
| Destructive — delete event | Action: "Xóa sự kiện" · Confirm: "Xóa sự kiện “{tên sự kiện}”? Toàn bộ cấu hình và lịch sử ảnh sẽ mất. Không thể hoàn tác." |
| Destructive — clear photo history | Action: "Xóa lịch sử ảnh" · Confirm: "Xóa toàn bộ lịch sử ảnh của sự kiện này? Không thể hoàn tác." |
| Destructive — log out | Action: "Đăng xuất" · Confirm: none required (non-destructive to data, session-only) |

### Room Screen default copy (CMS-01-editable per event; these are the shipped defaults)

| Element | Copy |
|---------|------|
| Idle/standby heading (UI-01) | "Sẵn sàng chụp ảnh cùng bạn" |
| Idle/standby sub / QR CTA | "Quét mã QR bên dưới để đăng ký" |
| Announcing greeting (proven copy, carried from `displayPage.ts`) | "Xin mời {tên khách}" |
| Busy/capturing copy (proven copy, carried from `displayPage.ts`) | "Đang chụp ảnh.<br>Hãy nhìn vào ống kính." |
| Countdown instruction | "Chuẩn bị trước máy ảnh — phiên chụp sắp bắt đầu." |

### Room Screen system copy (fixed — never event-editable, operational signals)

| Element | Copy |
|---------|------|
| Feed disconnected (WS `/display` drops) | "Mất kết nối — đang thử kết nối lại…" (matches the reconnect copy already proven in both incumbents) |
| Agent offline | "● Agent mất kết nối" |
| Agent online | "● Agent đang kết nối" |

## UI Considerations

Applicable state considerations resolved: **18 covered, 2 backstop, 0 unresolved.**
Provenance: the researcher authored the base table; the ui-consideration-probe engine then
ran post-verification over 6 element surfaces (Room Screen, CMS login, event list, config
form, photo history, Agent config) and proposed 44 category×element candidates. Cross-checking
those against this table surfaced 4 genuine gaps (G1–G4 below), resolved by the human on
2026-08-12 together with the font-list question; the logo-aspect row was closed with the
defensible default it already proposed (orchestrator call, concrete acceptance criterion —
not a human answer).

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Room Screen — no guest yet (UI-01) | ✅ covered | Dedicated idle state renders on open, before any webhook/guest exists — see Copywriting Contract "Idle/standby heading". Not a blank screen. |
| empty | CMS — event list, zero events | ✅ covered | "Chưa có sự kiện nào" heading + "Tạo sự kiện đầu tiên…" body + the "+ Tạo sự kiện mới" CTA, not a blank table. |
| empty | CMS — photo history, zero photos | ✅ covered | "Chưa có ảnh nào" heading + body copy above. |
| error | Room Screen — WS `/display` feed disconnects mid-session | ✅ covered | Distinct "Mất kết nối — đang thử kết nối lại…" state, never a silent freeze on the last-known screen — direct extension of UI-01's "nobody yet ≠ broken" principle to connection loss, which is not otherwise covered by SC-2 as literally written. |
| error | CMS — login failure | ✅ covered | "Sai tên đăng nhập hoặc mật khẩu…" — see Copywriting Contract. |
| error | CMS — save config fails | ✅ covered | "Không lưu được cấu hình…" — see Copywriting Contract. |
| error | CMS — Agent connection test fails (UI-02) | ✅ covered | "Không kết nối được Agent…" — see Copywriting Contract. |
| zero-one-many | Room Screen — photo slideshow / recent photos | ✅ covered | 0 photos → idle state (see empty, above); 1 photo → single static slide, no rotation/dots; many → rotates at the configured per-photo duration (CMS-01), default 6s, matching the incumbent's proven default. |
| zero-one-many | Room Screen — up-next queue sidebar | ✅ covered | 0 upcoming → sidebar shows the fixed "Hàng chờ đang được cập nhật…" / empty-queue copy already proven in `displayPage.ts`; 1..N renders the list; see overflow row below for many. |
| overflow | Room Screen — up-next queue sidebar, many guests | ✅ covered | Scrollable list, capped visible rows, `overflow-y:auto` — carried forward from the incumbent `web-slide` sidebar pattern, already proven. |
| overflow / long-text | Room Screen — guest hero name (Vietnamese, can be long with diacritics) | ✅ covered | Hero name uses `overflow-wrap:anywhere` + fluid `clamp()` sizing to shrink-to-fit rather than truncate (proven pattern, `displayPage.ts`); queue-sidebar row names truncate with ellipsis instead (space-constrained list context, different rule for a different container — both from the incumbent). |
| partial | CMS — event config saved incomplete/partial (operator saves before finishing every CMS-01 field) | ✅ covered | Every CMS-01 field has a system default (see Room Screen default copy + default theme above); an event can go live with zero customization and still render correctly. | media | Room Screen — guest with no photo (no_photo outcome, or guest departs before completion) | ✅ covered | Slideshow skips a no_photo guest entirely; if a name-only fallback tile is ever shown, reuse the incumbent's initials-avatar fallback (`getInitials()` + gradient avatar), not a blank/broken image icon. |
| loading | CMS — save config in flight | 🧪 backstop | Button shows a disabled+spinner state while the save request is in flight, so a double-click cannot fire two writes. No explicit test authored yet — verify-time evidence required (held-out UI-state check or equivalent), not a silent pass. |
| loading | Room Screen — initial WS `/display` connect, before first snapshot arrives | 🧪 backstop | Renders the same idle/standby state as "no guest yet" while waiting for the first snapshot (not a separate spinner) — the WS client already receives an immediate snapshot on connect per `displayServer.ts`, so this window is normally sub-second; still needs an explicit check that it never flashes unstyled/blank HTML first. |
| overflow | CMS — event logo, arbitrary uploaded aspect ratio | ✅ covered | `object-fit: contain` inside a bounded box — never stretched, never cropped. Closed with the defensible default this row originally proposed (orchestrator call, 2026-08-12; testable criterion, not a taste question). |
| — | Room Screen — curated font list contents | ✅ covered | **Human-answered 2026-08-12:** 3 options in the CMS-01 font picker — (1) system-ui (default, zero extra bytes), (2) Be Vietnam Pro (sans, designed for Vietnamese, OFL), (3) Lora (serif, good Vietnamese diacritics, OFL). All self-hosted in the service, weights 400+700 only, never a CDN `<link>`. |
| loading | CMS — every mutating control, generalized (G1) | ✅ covered | **Human-answered 2026-08-12:** the disabled+spinner in-flight contract declared for "Lưu cấu hình" applies to EVERY mutating control — login submit, delete/trash, uploads, "Kiểm tra kết nối". | overflow | CMS — event list & photo history, many rows (G2) | ✅ covered | **Human-answered 2026-08-12:** photo history paginates at 50/page (newest first); event list scrolls (operator event counts are small). No unbounded DOM lists. |

| media | CMS — broken/missing photo thumbnail in history (G4) | ✅ covered | **Human-answered 2026-08-12:** a thumbnail that fails to load renders a neutral placeholder tile with the warning icon + visible Vietnamese label — never the browser's broken-image glyph. ## Open Questions — status after the 2026-08-12 human session

Four of the five were put to the human via AskUserQuestion on 2026-08-12 (or closed with a
stated defensible default); their decisions are now LOCKED for planning. One remains, and it
is the planner's by design.

1. **Room Screen curated font list — ANSWERED (human, 2026-08-12).** The CMS-01 font picker
   ships exactly 3 options: (1) **system-ui** — default, zero extra bytes; (2) **Be Vietnam
   Pro** — sans, designed for Vietnamese, OFL; (3) **Lora** — serif, strong Vietnamese
   diacritic support, OFL, for formal/wedding events. All self-hosted inside the service
   (never a Google Fonts / CDN `<link>` — venue wifi cannot be a dependency), weights
   400+700 only (~a few hundred KB total). Licence note for the executor: bundle the OFL
   licence files alongside the font binaries.
2. **Room Screen "layout style" — ANSWERED (human, 2026-08-12): default layout only this
   phase.** Ship exactly one layout — the incumbent's proven stage+sidebar two-column grid
   (hero/photo left, up-next queue right, collapsing to one column under a documented
   breakpoint). The `layout_style` field still EXISTS in the event config schema with this
   single value, so later phases add layouts without a schema migration. Additional layouts
   are explicitly out of scope; the planner must not grow the display test matrix for
   hypothetical layouts.
3. **CMS login model — ANSWERED (human, 2026-08-12): single operator account.** One
   username/password pair configured via `.env` (password stored as a hash, never
   plaintext), HttpOnly session cookie, **no automatic inactivity timeout** — an event runs
   for hours and being ejected to a login screen mid-event is operationally worse than the
   session lingering; logout is manual. No user table, no account CRUD, no reset flow this
   phase.
4. **CMS event → Room Screen URL contract (CMS-02) — STILL OPEN, deliberately for the
   planner.** Architecture, not visual contract (`/display/:eventSlug` vs. query param vs.
   per-screen token). The visual requirement that IS locked: the CMS surfaces a copyable
   "Screen URL" per event so an operator can point a TV at the right event without typing in
   a URL bar under pressure. Planner should weigh the existing `WS /display` allow-list
   gating (`displayServer.ts`, D-09) when choosing the scheme.
5. **Logo aspect-ratio handling — CLOSED with the stated default** (`object-fit: contain`
   in a bounded box, never stretched/cropped) — see UI Considerations table. Orchestrator
   call on a testable criterion, recorded as such rather than as a human answer.
