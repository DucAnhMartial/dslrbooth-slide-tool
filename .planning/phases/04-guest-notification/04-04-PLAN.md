  <action>
Write a new `## 8. Guest notification delivery` section at the end of the runbook, in the same register as §6 and §7 — declarative, quoting real strings, no marketing. Cover, in this order:

**The published payload contract.** The exact five keys this service POSTs to `NOTIFY_WEBHOOK_URL`, with a real example body. State plainly that the receiver performs no lookup of any kind — it reads fields straight off the request body and falls back silently when one is absent — so anything the slideshow shows must be in the payload, and a field rename on either side produces a blank display and no error anywhere (D-01). Name which receiver fields this service deliberately leaves unpopulated and why: the slideshow displays a name and an image and has no use for contact details, so none are sent, and not sending them is cheaper than protecting them in transit (D-02, D-03). Note that this webhook is unsigned, unlike the inbound `/on-register` contract in §1, and that the reason is the absence of personal data in the body — if that ever changes, signing must be revisited.

**The delivery model.** One paragraph: an Agent `file_upload` event writes a durable work item to `notification_record` carrying the photo URL, and a periodic sweeper delivers rows that are due. There is no in-memory retry loop and no startup recovery pass; the sweeper's own due-time query is the recovery mechanism, which is what makes a restart mid-retry harmless (D-04). Say explicitly that a process killed mid-delivery leaves its row claimed with a lease, and that the row becomes deliverable again on its own when that lease expires.

**The status vocabulary.** A table of the five values a `notification_record` row can hold — `pending`, `retrying`, `sending`, `delivered`, `failed` — what each means operationally, whether it is terminal, and what makes a row leave it. Note that `sending` carries a lease deadline in `dueAt` rather than being a dead end, and that the two terminal states are excluded from every query the sweeper runs, which is what guarantees a guest's photo is never sent twice (D-05).

**The failure vocabulary.** The `lastError` reason strings the code actually writes, quoted from `04-02-SUMMARY.md`, with what each tells the operator — in particular that a timeout means the receiver is alive and stuck while a connection failure means it is absent, and that these lead to different fixes. Quote the exhaustion log line verbatim so it can be grepped, following §7's precedent of quoting log lines exactly as the code emits them.

**Finding guests who never got their photo.** The concrete `SELECT` joining `notification_record` to `queue_job` and `registration` that lists failed deliveries with the guest's name and the recorded reason. This is what D-09 exists for and what NOT-02's "log để xử lý thủ công" means in practice.

**Re-arming a failed notification by hand.** The `UPDATE` that resets a row to `pending` with a due time of now, preceded by the same backup warning §6 uses for its manual SQL. State the deliberate design point that the code will not do this for you: a repeat `file_upload` for a job whose notification already reached a terminal state does not re-arm it, because terminal is terminal, and an explicit operator action is the intended path.

**The retry budget.** `NOTIFY_MAX_RETRIES` counts retries *after* the first attempt, so the shipped default of 2 yields 3 total attempts. Note that this meaning changed in this phase and that the default moved from 3 to 2 in the same change specifically so the real number of attempts stayed at 3 — anyone who set this variable explicitly in a production environment file is now getting one more attempt than before and should re-read their value.

**One migration note, stated plainly.** The first boot after this deploy rewrites rows: any `notification_record` row predating the change has no photo URL and can never be delivered, so the migration marks it terminally failed with the marker string quoted from `04-01-SUMMARY.md`. This is one-way. It is honest rather than silent — the alternative was leaving those rows looking deliverable forever.

Then extend `## 3. Environment variables that must be set before a production deploy` with the three new variables — `NOTIFY_FETCH_TIMEOUT_MS`, `NOTIFY_SWEEP_INTERVAL_MS`, `NOTIFY_CLAIM_LEASE_MS` — matching the table's existing columns and stating each default. Add a row for `NOTIFY_WEBHOOK_URL` if §3 does not already carry one, noting that when it is unset the service warns and skips delivery rather than failing, which is safe but silent.

This task changes documentation only. Do not touch any file under `src/` or `test/`.
