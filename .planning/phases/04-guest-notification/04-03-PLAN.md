<objective>
Pin the storage contract that everything else in this phase rests on, at the level where it is actually enforced: the SQL.

Plan 04-01 delivered the schema change and the three new `LocalStore` methods and proved the happy path end to end. This plan proves the parts of that storage layer whose failure modes are *silent* — a migration that quietly does the wrong thing on the second boot, a status write that quietly nulls the photo URL, a repeat event that quietly re-arms a delivered notification. None of these would fail a delivery test; all of them would strand a guest.

Purpose: D-04's "restart-proof by construction" is only as true as the SQL predicates that carry it. Every guarantee in this phase lives in a `WHERE` clause or a `COALESCE`, deliberately, so that no future edit can weaken it without a test going red. This plan is that test.

Output: two new describe blocks in the existing real-file `LocalStore` harness, covering the migration's honesty and the persisted queue's SQL contract.

  <behavior>
    Add a second describe block covering the persisted-queue contract, against a real temp-path `LocalStore`. Each case names the guarantee it pins.

    - Test 1 — enqueue then due: `enqueueNotification({ jobId, photoUrl, dueAt: now })` makes the row visible to `getDueNotifications(now)` with the photo URL intact, and `getDueNotifications(now - 1000)` does not return it. The due predicate is a real time gate, not decoration.
    - Test 2 — a terminal row is not re-armed (D-05): enqueue, mark the row `delivered` through `saveNotification`, then call `enqueueNotification` again with the same job id. The row is still `delivered` and `getDueNotifications` returns nothing for it. Repeat the case for a `failed` row. This is the guarantee living in the `ON CONFLICT … WHERE status NOT IN ('delivered','failed')` clause, and it is the difference between one photo on the slideshow and two.
    - Test 3 — a status write does not erase the photo URL: enqueue with a photo URL, then call `saveNotification({ jobId, status: 'retrying', attempts: 1, dueAt: now })` supplying no photo URL, and assert the persisted URL is still there and the row is still returned by `getDueNotifications` with that URL. Without the `COALESCE` guard this is exactly where restart resumption would silently become impossible — the row would survive the restart carrying nothing to send.
    - Test 4 — claim transitions once (D-05): `claimNotification(jobId, now, now + lease)` returns true; an immediate second call with the same `now` returns false, because the first claim pushed the due time out to the lease deadline. Then assert `getDueNotifications(now)` no longer returns the row while `getDueNotifications(now + lease + 1)` does — the lease expiry is what lets a process that died mid-flight self-heal without any boot-time recovery pass.
    - Test 5 — a NULL photo URL is never due: write a row through `saveNotification({ jobId, status: 'pending', attempts: 0, dueAt: now })` with no photo URL, and assert `getDueNotifications(now)` does not return it. Belt and braces on top of the migration: nothing can ever be POSTed with nothing to send.
  </behavior>
