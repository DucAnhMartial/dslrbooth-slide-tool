<objective>
Replace the in-memory retry loop in `notificationService.ts` with a persisted retry queue, end to end, on one path: an Agent `file_upload` durably records a work item carrying the photo URL, and a periodic sweeper in a *different process lifetime* delivers it to `web-slide` with the exact payload the slideshow expects.

This is the phase tracer. It deliberately touches every layer this phase will modify — config, types, storage, service, bootstrap, test — doing the minimum in each, so an architectural dead end surfaces after one commit rather than after five. Failure-posture refinements (fetch timeout, error classification, the operator-facing exhaustion log line, per-row isolation) are expansion work in plan 04-02 and are explicitly NOT in this plan.

Purpose: today the retry loop lives in memory while `notification_record` persists to SQLite, and `photoUrl` has never been a persisted column at all. A restart mid-retry therefore strands a guest's photo permanently — structurally the same defect Phase 2 fixed in the booth state machine, one layer up (D-04, D-13).

Output: a working persisted-queue delivery path, proven by a real ephemeral HTTP server receiving a delivery that was enqueued by one `LocalStore`/`NotificationService` pair and delivered by a second pair opened on the same database file.

| Boundary | Description |
|----------|-------------|
| Agent WS → `queueService.onAgentEvent()` | `payload.photoUrl` arrives from the booth Agent — authenticated in Phase 3, but still external input that is now persisted and later replayed |
| `mirror-request` → `web-slide` HTTP | Outbound webhook across a process boundary on the same host; unsigned by deliberate decision (D-02's deferred idea) |
| `migrate()` → live production SQLite | This plan mutates rows in a database carrying real operational history |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-04-01 | Information Disclosure | outbound webhook payload | medium | mitigate | Payload is name + photo + jobId + mode + timestamp only (D-02); the exact-key `toEqual` assertions in Task 1 test 2 and Task 2 fail the suite if `phone`/`email` are ever re-added |
| T-04-02 | Tampering | `notification_record` migration | high | mitigate | Additive-only `ALTER TABLE`, no drop or recreate (localStore.ts:77-79's standing rule); backfill is narrowly predicated on `photoUrl IS NULL AND status NOT IN ('delivered','failed')` and gated on a column actually having been added; plan 04-04's blocking gate requires a backup before deploy |
| T-04-03 | Repudiation | delivery outcome | medium | mitigate | Every attempt writes `status`/`attempts`/`lastError` durably; un-resumable pre-migration rows are marked `failed` with a stated reason rather than left ambiguous (D-13) |
| T-04-04 | Denial of Service | sweeper loop | medium | accept in this plan | An unresponsive `web-slide` can hold one attempt open indefinitely because this plan deliberately omits the fetch timeout; closed by plan 04-02 Task 1 (D-07) in the same wave-2 merge |
| T-04-05 | Elevation of Privilege | n/a | low | accept | No authentication, authorization or cryptographic surface is added or changed by this plan |
| T-04-SC | Tampering | npm/pip/cargo installs | high | mitigate | Not applicable — this phase installs no external package (RESEARCH.md § Package Legitimacy Audit); `AbortSignal.timeout()` and `fetch` are Node 20 built-ins and `better-sqlite3` was audited in Phase 2. Any executor that finds itself running `npm install <pkg>` must stop and escalate. |
</threat_model>
