<objective>
**As a** booth operator, **I want to** start and configure the Agent from a window on the booth PC,
**so that** running a photo booth never depends on remembering a terminal command.
*(Phase story; this plan is the first slice of it — the lifecycle the window will drive.)*

Turn the Agent's startup wiring into a factory with an explicit lifecycle: `createAgent(config, logger)`
constructs the relay but binds nothing, `start()` opens the trigger port and dials the service,
`stop()` gives both back, and `getStatus()` answers the three questions an operator asks. The CLI
entry the booth PC runs today is rebuilt on top of that factory and behaves identically.

Purpose: this is the whole reason the desktop app is possible. Today `src/index.ts` binds `:3001`
and dials the socket at module load inside one `main()`; an Electron main process hosting that
would be relaying before the operator had configured anything or clicked Start — 10-RESEARCH's
Pitfall 4, and a direct contradiction of success criterion 2. Everything in this plan is provable on
this Linux machine, and every commit leaves `build:exe` green, because the booth PC keeps running
the pkg exe until the human gate at the end of the phase swaps it (D10-01).

Output: `src/agent.ts` (the factory), `src/commands.ts` (the `start_session` branch moved to a seam a
test can drive), `src/health/reachability.ts`, an error seam on the trigger server, a shared config
validator, a rebuilt `src/index.ts`, and three new test files including a genuine end-to-end
lifecycle test against a real WebSocket server and a real dslrBooth stub.
</objective>
